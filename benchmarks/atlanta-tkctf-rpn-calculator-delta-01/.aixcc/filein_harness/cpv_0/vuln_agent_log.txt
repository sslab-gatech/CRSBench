# Vulnerability Analyzer

Analyze a vulnerability from crash logs, POV files, patches, and source code to prepare for vuln.yaml generation.

## Analysis Strategy

### Step 1: Analyze Crash Log (CRITICAL - Start Here)

The crash log is the primary source of vulnerability information.

**CRITICAL**:
- **ONLY** read crash log files from the CPV's logs directory
- **DO NOT** search for crash logs from other CPVs

Find and read crash log files (e.g., `pov_0.log`, `crash.log`).

Extract key information:
- **Error type**: AddressSanitizer error (heap-buffer-overflow, use-after-free, etc.)
- **Vulnerable function**: The function where the crash occurred (from stack trace)
- **Vulnerable file**: The source file path (from stack trace)
- **Line number**: Exact line where crash happened
- **DEDUP_TOKEN**: Unique identifier for this crash
- **Stack trace**: Full call stack for understanding control flow

Example crash log parsing:
```
ERROR: AddressSanitizer: heap-buffer-overflow
READ of size 45 at 0x50400000033c
#0 __asan_memcpy /src/llvm-project/compiler-rt/lib/asan/...
#1 cr_buf_read /src/curl/lib/sendf.c:1298:5    <-- Vulnerable function
#2 Curl_creader_read /src/curl/lib/sendf.c:542:10
...
SUMMARY: AddressSanitizer: heap-buffer-overflow /src/curl/lib/sendf.c:1298:5 in cr_buf_read
```

From this, extract:
- Error type: heap-buffer-overflow
- File: lib/sendf.c (relative to project root)
- Function: cr_buf_read
- Line: 1298

### Step 2: Identify Location Types

For each vulnerability location, determine its type:

**crash_site**: The point where the program crashes or error is detected
- This is typically the location from the crash log stack trace
- MUST be in project code
- Example: The function where buffer overflow READ occurs

**root_cause**: The underlying defect that enables the vulnerability
- This is where the actual bug/defect exists
- May be different from crash site (e.g., missing bounds check, incorrect allocation)
- Example: Where buffer is allocated too small, or where bounds check is missing
- **IMPORTANT: Analyze patches to identify root_cause** - patches show exactly what was fixed

**EXCLUDE from both crash_site and root_cause:**
- Harness files (fuzzing harness code, e.g., `*_fuzzer.c`, `*_fuzzer.cc`, `LLVMFuzzerTestOneInput`)
- ASan/sanitizer functions (`__asan_*`, `__msan_*`, `__ubsan_*`)
- Standard library functions (`memcpy`, `malloc`, `free`, `strlen`, etc.)
- Compiler runtime functions (`__interceptor_*`, `llvm-project/compiler-rt/*`)
- Only include actual project source code locations

### Step 3: Locate Vulnerable Code

- Use the file path from crash log to find the vulnerable source file
- Read the vulnerable file around the crash line number
- Identify the exact vulnerability location
- Note the function name, line numbers, and code context

### Step 4: Analyze POV (if available)

- Check the CPV's blobs/ directory for POV files
- These are test inputs that trigger the vulnerability
- Note if POV structure provides hints about vulnerability type

### Step 5: Analyze Patches (CRITICAL for root_cause)

- Check the CPV's patches/ directory for patch files
- **Patches are the primary source for identifying root_cause location**
- Analyze what was changed to fix the vulnerability:
  - Which file(s) were modified?
  - Which function(s) were changed?
  - What line(s) were added/removed?
- The patch location typically indicates the root_cause location
- If patch differs from crash site, you likely have separate crash_site and root_cause

### Step 6: Identify Vulnerability Origin and Reference

**⚠️ CRITICAL: DO NOT GUESS. ONLY USE CONCRETE EVIDENCE. ⚠️**

**origin**: Source of the vulnerability
- `1-day`: Real-world vulnerability with confirmed official reference (CVE, OSV, GHSA, bug tracker, etc.)
- `synthetic`: Everything else (DEFAULT)

**🚨 RULES FOR 1-day CLASSIFICATION 🚨**

1. **Start with patch files** - Extract key information:
   - Function name(s) being patched
   - File path(s) being modified
   - Type of fix (bounds check, null check, etc.)
   - Any vulnerability ID already mentioned in patch (CVE, OSV, GHSA, issue #)

2. **Search based on patch content:**
   - Use WebSearch with: project name + function name + vulnerability keywords
   - Example: `libtiff TIFFReadRawStrip1 CVE` or `libtiff TIFFReadRawStrip1 vulnerability`
   - Look for an EXACT match - same function, same fix

3. **Confirm the match:**
   - The reference must describe the EXACT same vulnerability
   - Same function name
   - Same type of bug
   - Same file/location
   - If it's just "similar" but not exact → `synthetic`

4. **DO NOT mark as `1-day` based on:**
   - ❌ "Similar looking" vulnerabilities
   - ❌ Same project but different function
   - ❌ Same bug type but different location
   - ❌ Guessing or "it might be"

5. **If no EXACT match found → `synthetic`**

**How to check (in order):**
1. Read patch files - note function names, file paths, fix type
2. Check if vulnerability ID already in patch content/filename (CVE, OSV, issue #)
3. Check `.aixcc/meta.yaml` for existing reference
4. WebSearch: `[project] [function_name] vulnerability` or `CVE` (only if needed)
5. WebFetch: Get release_date from the reference source
6. If no exact match → `synthetic`

**release_date**:
- For 1-day: Fetch from the official reference source (NVD, OSV, GitHub advisory, etc.)
- For synthetic: Use `02/01/2026`

**references**: List of URLs to vulnerability details (REQUIRED for 1-day)
- Include all confirmed references (a single vulnerability may have multiple)
- Valid reference sources:
  - CVE: `https://nvd.nist.gov/vuln/detail/CVE-XXXX-XXXXX`
  - OSV: `https://osv.dev/vulnerability/OSV-XXXX-XXXX`
  - GHSA: `https://github.com/advisories/GHSA-xxxx-xxxx-xxxx`
  - Project bug tracker: `https://github.com/project/issues/XXX`
  - Other official security advisories
- Example: A vulnerability may have both CVE and GHSA references

**Root Cause (main_loop function at lines 244-254):**
```c
else if ( in == 'w' ) {
    // leave START - 1 as null byte to catch the first word on stack
    int widx = CHILD_SIZE - 2;
    for ( int i = a.idx - 1; 
          (wchar_t)values[i] != 0;   // BUG: No bounds check on 'i'
          i--, widx-- )               // BUG: No bounds check on 'widx'
    { 
        wcs[widx] = (wchar_t)values[i];

    print_utf8(wcs + widx + 1);

```

**Understanding the vulnerability:**

The code defines:
- `STACK_SIZE = 0x20 (32)`
- `CHILD_SIZE = STACK_SIZE / 2 = 16`
- `START = CHILD_SIZE = 16`
- `END = STACK_SIZE = 32`

The struct A has:
```c
typedef struct {
    int idx;
    int values[STACK_SIZE];  // Array of 32 ints
} A;
```

In main_loop, the 'pw' (print wide character) command iterates backwards through the stack:
1. Starts at `i = a.idx - 1` and decrements `i`
2. Continues while `(wchar_t)values[i] != 0`
3. **CRITICAL BUG**: There's no check to prevent `i` from going below 0 or `widx` from going negative
4. If the stack contains no null values, `i` will decrement past 0 into negative indices
5. This causes `values[i]` to read beyond the stack frame bounds
6. Similarly, `widx` can become negative, causing `wcs[widx]` to write to invalid memory
7. Later, when `dump()` is called with the corrupted index, it reads from freed/invalid stack memory

## CWE Classification
- **CWE-787**: Out-of-bounds Write (widx can go negative, writing to wcs array)
- **CWE-125**: Out-of-bounds Read (i can go negative, reading from values array)
- **CWE-121**: Stack-based Buffer Overflow (accessing memory beyond stack frame bounds)
- **CWE-843**: Access of Resource Using Incompatible Type ('Type Confusion') - treating int array as wchar_t array

## Vulnerability Description

This is a **stack buffer underflow vulnerability** in the RPN calculator's 'pw' (print wide character) command implementation. 

**Root Cause:**
The vulnerability exists in the `main_loop()` function at lines 244-254, where the code processes the 'pw' command to print wide characters from the stack. The loop iterates backwards through the `values` array starting from `a.idx - 1`, but **fails to check if the loop index `i` goes below the minimum valid index (START or 0)**. The loop only checks if the value is non-zero: `(wchar_t)values[i] != 0`.

**Attack Scenario:**
1. An attacker crafts input that fills the stack with non-zero values
2. When the 'pw' command is executed, the loop begins at `a.idx - 1`
3. Since all values are non-zero, the loop continues decrementing `i` past valid bounds
4. `i` becomes negative, accessing memory before the `values` array
5. Simultaneously, `widx` (initialized to `CHILD_SIZE - 2 = 14`) also decrements without bounds checking
6. Both `values[i]` (read) and `wcs[widx]` (write) access invalid memory locations
7. This corrupts the stack and leads to a stack-use-after-return condition when `dump()` later attempts to read from the corrupted index

**Impact:**
- Memory corruption due to out-of-bounds read and write operations
- Stack-use-after-return crashes
- Potential for arbitrary code execution if an attacker can control the corrupted memory

## POV Analysis

The POV file (pov_0.blob) is a carefully crafted input that triggers this vulnerability:

```
c -18 0x41 0x42 0x43 0x44 0x45 0x46 0x47 0x48 0x49 0x4a 0x4b 0x4c 0x4d 0x4e 0x4f pw
```

The input:
1. Uses 'c' command with negative index `-18` to manipulate the stack pointer
2. Pushes multiple non-zero hex values (0x41-0x4f, which are ASCII 'A'-'O')
3. Executes 'pw' command to trigger the vulnerable loop
4. The pattern repeats with variations (`-17`, `-19`, `-20`, `-21`, `-22`, `-305`) to ensure the vulnerability is triggered
5. The large negative value `-305` likely causes significant stack manipulation
6. The lack of null bytes in the pushed values ensures the loop condition `(wchar_t)values[i] != 0` remains true
7. This forces the loop to continue past valid array bounds, triggering the stack-use-after-return

## Patch Analysis

The patch (patch_0.diff) fixes the vulnerability by adding a bounds check to the loop condition:

**Original (vulnerable) code:**
```c
for ( int i = a.idx - 1; 
      (wchar_t)values[i] != 0;   // Only checks for null
      i--, widx-- )
```

**Patched code:**
```c
for ( int i = a.idx - 1; 
      ((wchar_t)values[i] != 0) && (widx >= 0);  // Added bounds check
      i--, widx-- )
```

**Key Changes:**
1. Added `&& (widx >= 0)` to the loop condition
2. This ensures the loop terminates when `widx` reaches 0, preventing negative index access
3. The comment was updated from "leave START - 1 as null byte to catch the first word on stack" to "iterate backwards until end of stack or null byte"
4. This prevents both the buffer underflow on `wcs[widx]` write and the out-of-bounds `values[i]` read

**Why this fixes the vulnerability:**
- The bounds check `widx >= 0` ensures the loop cannot continue indefinitely
- Since `widx` is initialized to `CHILD_SIZE - 2` (14) and decrements in sync with `i`, the check prevents accessing negative indices
- This limits the backward iteration to at most 15 elements (from index 14 down to 0)
- Even if all values are non-zero, the loop will terminate when it reaches the beginning of the buffer

## Recommendations

**Suggested CWEs:** 
- Primary: CWE-787 (Out-of-bounds Write)
- Secondary: CWE-125 (Out-of-bounds Read)
- Tertiary: CWE-121 (Stack-based Buffer Overflow)

**Vulnerability Name:** "Stack Buffer Underflow in RPN Calculator Wide Character Print Command"

**Additional Security Improvements:**
1. Add bounds checking for the `i` variable as well: `(i >= START) && (widx >= 0)`
2. Consider using safer array access patterns with explicit bounds validation
3. Add assertions or runtime checks for all array index operations
4. Consider using pointer arithmetic with bounds checks instead of potentially negative indices
5. Validate that `a.idx` is within valid range before entering the loop
